SECTION 01
System Architecture Overview
How all services connect and what each layer is responsible for
What CodeCompass Does
CodeCompass is a three-tier web application. A user submits a GitHub repository URL through the React frontend. The Java Spring Boot backend orchestrates the entire intelligence pipeline: it calls the GitHub API to fetch the repository, sends the source files to a Python FastAPI micro-service that performs AST parsing, dependency graph construction, and vector embedding generation, stores all structured results in PostgreSQL (hosted on Supabase), and makes the embedded chunks queryable via FAISS for RAG-powered conversational queries. The user then interacts with the results through four major features: an interactive architecture map, a bug-risk heatmap overlay, a conversational chat grounded in the actual codebase, and an AI-generated onboarding checklist.
Four-Service Architecture
▸  React Frontend (Vercel) — All user interaction. Communicates with the Spring Boot backend exclusively via REST API and JWT-authenticated headers. Never calls GitHub or Gemini directly.
▸  Java Spring Boot Backend (Render) — The orchestration brain. Owns authentication, authorization, all business logic, job management, GitHub API communication, Supabase database access, and all external API calls. Exposes a versioned REST API on /api/v1/.
▸  Python FastAPI Service (Render) — The intelligence engine. Receives raw source files from the Java backend, performs AST parsing, builds dependency graphs using NetworkX, computes complexity metrics, generates vector embeddings using the Gemini Embedding API, and persists embeddings in a FAISS index. Stateless — the Java backend controls all state.
▸  PostgreSQL on Supabase — Single source of truth for all persistent data: users, repositories, analysis results, dependency graphs, chat history, and onboarding progress. FAISS index files are stored on Render's persistent disk, with their index IDs tracked in PostgreSQL.
Request Flow — From URL Paste to Intelligence
▸  1. User pastes a GitHub URL into the frontend and clicks Analyze Repository.
▸  2. Frontend sends POST /api/v1/repos/analyze with the GitHub URL and JWT token.
▸  3. Spring Boot validates the JWT, extracts the user ID, creates a Repository record in PostgreSQL with status PENDING, and returns a jobId immediately — the response is instant.
▸  4. Spring Boot spawns an @Async background thread. This thread calls the GitHub REST API to fetch the repository tree and all file contents up to 1MB per file.
▸  5. Spring Boot sends all raw file contents to POST /internal/parse on the Python service.
▸  6. Python service: runs AST parsing on every supported file, extracts function signatures and class hierarchies, builds a NetworkX dependency graph, computes cyclomatic complexity and churn risk scores, generates vector embeddings via the Gemini Embedding API, and persists a FAISS index to disk. Returns structured JSON.
▸  7. Spring Boot receives the structured results, writes everything to PostgreSQL (files, functions, edges, hotspots, summaries, FAISS index ID), updates the Repository status to COMPLETED.
▸  8. WebSocket push notifies the frontend that analysis is complete.
▸  9. Frontend navigates the user to the Workspace.
ℹ  NOTE
Every backend operation after step 3 is asynchronous and non-blocking. The user's HTTP connection is never held open during analysis. The frontend polls GET /api/v1/repos/{repoId}/status every 3 seconds and receives WebSocket push when done.

SECTION 03
Authentication & Authorization
Every login flow, token lifecycle, and access rule
Authentication Strategy
CodeCompass uses two authentication methods: GitHub OAuth 2.0 (primary, recommended) and email/password with bcrypt hashing (secondary). Both flows produce identical JWT access tokens on completion — the rest of the application cannot distinguish between the two auth methods.
GitHub OAuth Flow (Primary)
▸  1. User clicks Continue with GitHub on the Auth page. Frontend redirects to: GET /api/v1/auth/github — Spring Boot redirects to GitHub's OAuth authorization URL with client_id, scope=read:user user:email repo, and a state nonce.
▸  2. GitHub redirects back to: GET /api/v1/auth/github/callback?code=...&state=... — Spring Boot validates the state nonce, exchanges the code for a GitHub access token via POST to https://github.com/login/oauth/access_token.
▸  3. Spring Boot calls GET https://api.github.com/user and GET https://api.github.com/user/emails with the GitHub token to fetch the user's profile and verified email.
▸  4. Spring Boot upserts a row in the users table (INSERT if new user, UPDATE github_access_token if returning user). The GitHub access token is AES-256 encrypted before storage.
▸  5. Spring Boot generates a JWT access token (15-minute expiry, RS256 signed) and a refresh token (30-day expiry, stored hashed in refresh_tokens table). Both are returned in the response body (not in cookies, to avoid CSRF complications with CORS).
▸  6. Frontend stores the access token in memory (not localStorage) and the refresh token in an HttpOnly cookie.
Email/Password Flow (Secondary)
▸  Registration: POST /api/v1/auth/register — validates email uniqueness, bcrypt-hashes the password with cost factor 12, inserts user row, returns JWT pair.
▸  Login: POST /api/v1/auth/login — fetches user by email, verifies bcrypt hash, returns JWT pair.
▸  Password is never stored in plaintext, never logged, and never returned in any API response.
Token Lifecycle
▸  Access token: RS256 JWT, 15-minute expiry. Payload contains userId, email, and plan. Sent as Authorization: Bearer <token> header on every authenticated request.
▸  Refresh token: 256-bit random string, SHA-256 hashed before storage. 30-day expiry. POST /api/v1/auth/refresh validates the hashed token, revokes the old one, and issues a new pair (token rotation).
▸  Logout: POST /api/v1/auth/logout — marks all refresh_tokens for this user as revoked=TRUE.
Authorization Rules
▸  Every authenticated endpoint validates the JWT on every request. No session state is stored on the server — the backend is fully stateless.
▸  Row-level authorization: every database query for repositories, files, chat sessions, and onboarding data includes WHERE user_id = :authenticatedUserId. A user can never access another user's data even if they know a valid ID.
▸  Repository access: the user can only query or chat about repositories in their own repositories table. The faiss_index_id is resolved server-side; the frontend never receives a raw filesystem path.
▸  GitHub token scoping: the stored GitHub access token is only used to fetch private repositories. If the user revokes GitHub access, all subsequent analyses of their private repos will fail gracefully with a clear error message asking them to reconnect.

SECTION 04
Page-by-Page Backend Specification
What every button click triggers, from frontend action to database write
PAGE 1 — Authentication Page
Continue with GitHub Button
Frontend navigates to GET /api/v1/auth/github. Spring Boot generates a random state nonce, stores it in a 5-minute TTL Redis cache entry keyed by the nonce itself, then builds the GitHub OAuth URL and redirects. On callback, the state is validated, exchanged for a token, and the user is upserted as described in Section 3. The frontend receives the JWT pair and stores them. No user input beyond the button click.
Sign In Button (Email/Password)
Frontend sends POST /api/v1/auth/login with {email, password}. Spring Boot fetches the user record by email (index on users.email guarantees O(1) lookup), calls BCrypt.checkpw(rawPassword, storedHash), and returns 401 Unauthorized with error message Invalid email or password if the check fails. If successful, a JWT pair is returned. The same generic error message is used for both wrong email and wrong password to prevent user enumeration.
Create Account Button
Frontend sends POST /api/v1/auth/register with {fullName, email, password}. Spring Boot validates: email format regex, password minimum 8 characters with at least one number, email not already in users table. If email exists, returns 409 Conflict with message An account with this email already exists. If validation passes, bcrypt-hashes the password, inserts the user, and returns the JWT pair.
Forgot Password Link
Frontend sends POST /api/v1/auth/forgot-password with {email}. Spring Boot always returns HTTP 200 with message If that email exists, a reset link has been sent — regardless of whether the email is found, to prevent user enumeration. If the email exists, Spring Boot generates a password reset token (UUID, stored hashed in a password_reset_tokens table with 1-hour expiry) and sends an email via the configured SMTP provider (SendGrid free tier is sufficient for portfolio scale).
PAGE 2 — Landing Page
This is a static public page. No backend calls are made on page load. The only backend interaction is the Analyze Repository CTA, which triggers the same repository analysis flow described under Page 3 below. The Paste GitHub URL bar on this page is simply an entry point — submitting it navigates the user to the Auth page if they are not logged in, or proceeds to analysis if they are authenticated.
PAGE 3 — My Repositories Dashboard
Page Load — Fetching Repository List
On mount, the frontend sends GET /api/v1/repos. Spring Boot queries SELECT * FROM repositories WHERE user_id = :userId ORDER BY analyzed_at DESC. Returns an array of repository summaries including id, github_owner, github_name, description, primary_language, language_breakdown, status, file_count, function_count, hotspot_count, analyzed_at. The frontend renders one card per row. Repositories with status PENDING or FAILED show a different UI state (amber pulsing badge / red error badge respectively).
Open Workspace Button (on a Repo Card)
Frontend navigates to /workspace/:repoId. No additional API call — the repoId is already in the card data from the list fetch. The workspace page load triggers its own data fetches described under Page 4.
Re-analyze Button (on a Repo Card)
Frontend sends POST /api/v1/repos/:repoId/reanalyze. Spring Boot resets the repository status to PENDING, clears all existing repo_files, repo_functions, dependency_edges, onboarding_steps, and vector chunks associated with this repo_id, and re-queues the full analysis pipeline. This also deletes the old FAISS index file from disk and will generate a new faiss_index_id. Returns 202 Accepted with the repoId.
Analyze New Repository — Input + Button
Frontend sends POST /api/v1/repos/analyze with {githubUrl}. Spring Boot validates: URL matches pattern https://github.com/{owner}/{name}, the combination of (user_id, github_owner, github_name) does not already exist with status COMPLETED (prevent duplicate analysis). If the user's plan is free and they already have 5 repositories, return 403 Forbidden with message Free plan is limited to 5 repositories. Otherwise creates the repository record and starts the async analysis pipeline. Returns {repoId, status: PENDING} immediately.
PAGE 4 — Repository Analysis Loading Screen
Progress Polling
Immediately after receiving a repoId from the analyze endpoint, the frontend begins polling GET /api/v1/repos/:repoId/status every 3 seconds. This endpoint returns {status, analysis_progress, analysis_step, error_message?}. The frontend renders the progress bar and step checklist from this response. Spring Boot updates these fields on the repository row at each pipeline stage transition. Polling stops when status is COMPLETED or FAILED.
WebSocket Push (supplement to polling)
Spring Boot also maintains a WebSocket connection on /ws/analysis/{repoId}. When the analysis completes, a message {type: ANALYSIS_COMPLETE, repoId} is pushed. The frontend immediately stops polling and navigates to the workspace without waiting for the next poll interval. This prevents a worst-case 3-second delay after completion. The WebSocket uses STOMP protocol over SockJS (same pattern as ScheduleIQ).
Cancel Analysis Button
Frontend sends DELETE /api/v1/repos/:repoId/analysis. Spring Boot sets a cancellation flag in Redis (key: cancel:{repoId}, TTL 5 minutes). The background analysis thread checks this flag before each pipeline stage and exits cleanly if set. The repository row is deleted from PostgreSQL. Returns 200 OK immediately.
The Full Analysis Pipeline (Backend Deep Dive)
This is what happens inside the Spring Boot @Async thread after the repository record is created:
▸  Stage 1 — CLONING (updates status, progress=10, step='Connecting to GitHub API...'): Spring Boot calls GET https://api.github.com/repos/{owner}/{name} to validate the repo exists and fetch metadata. Then calls GET https://api.github.com/repos/{owner}/{name}/git/trees/main?recursive=1 to retrieve the full file tree. For each file in the tree, calls GET https://api.github.com/repos/{owner}/{name}/contents/{path} to fetch raw file content. Files larger than 1MB are skipped and recorded as too_large=TRUE on their repo_files row. Binary files (images, compiled files) are filtered out by extension. All file content is accumulated in memory.
▸  Stage 2 — PARSING (progress=35, step='Running AST Code Parsing across N files...'): Spring Boot sends a POST /internal/parse request to the Python FastAPI service with all file contents as a JSON payload. The Python service iterates over each file: for Python files, uses the built-in ast module to extract all function definitions (ast.FunctionDef), class definitions (ast.ClassDef), and import statements (ast.Import, ast.ImportFrom). For TypeScript/JavaScript files, uses tree-sitter-python or regex-based extraction of function/class declarations. For Java files, uses a regex pattern for method signatures. Each function's cyclomatic complexity is computed by counting branches (if, for, while, try, and, or nodes in the AST). Returns structured JSON with one entry per file.
▸  Stage 3 — GRAPH (progress=55, step='Building Dependency Graph...'): Python service uses all extracted import statements to build a directed NetworkX DiGraph. Each file is a node; each import that resolves to another project file is an edge. Computes node centrality (betweenness centrality — files depended on by many others score high). Identifies entry point files as nodes with zero in-degree (nothing imports them, they import others). Serializes the graph as edge-list JSON and returns it.
▸  Stage 4 — EMBEDDING (progress=70, step='Generating Vector Embeddings...'): Python service chunks each file's raw content into 512-token overlapping chunks (128-token overlap between consecutive chunks). Calls the Gemini Embedding API (models/text-embedding-004) for each chunk in batches of 100. Receives 768-dimensional float vectors. Builds a FAISS IndexFlatL2 index from all vectors. Saves the FAISS index to a file named {repoId}.faiss on Render's persistent disk. Records a chunk-to-file mapping in memory for citation resolution. Returns the faiss_index_id and total chunk count.
▸  Stage 5 — SUMMARIZING (progress=88, step='Generating Plain-English Summaries...'): Spring Boot calls Gemini Flash API for three types of summaries: (a) a whole-repository summary using the top 5 entry-point file summaries as context, (b) per-file summaries for every file using the first 2,000 characters of raw content plus the function signatures extracted by AST, (c) per-function summaries for every function — prompt includes the function signature, the function body up to 60 lines, and the containing file path. All summaries are written to the ai_summary columns in repo_files and repo_functions.
▸  Stage 6 — ONBOARDING (progress=95, step='Generating Onboarding Checklist...'): Spring Boot calls Gemini Flash with a prompt containing the repository summary, the top 20 files by centrality score, and the entry point files. Prompts Gemini to order these files into a reading path (max 9 steps) and generate a one-sentence reason for each. The JSON response is parsed and inserted as rows into onboarding_steps.
▸  Stage 7 — COMPLETE (progress=100, status='COMPLETED'): Spring Boot updates the repository row, fires the WebSocket push, and the pipeline thread exits.
ℹ  NOTE
The Python service is stateless. It receives all file content on each call and returns results. It does not access the database. The Java backend is the only service that writes to PostgreSQL. This clean boundary means the Python service can be scaled, restarted, or replaced independently.
SECTION 05
Workspace — Per-Tab Backend Specification
Every action inside the core SPA and what it triggers
Workspace Shell Load
When the user navigates to /workspace/:repoId, the frontend makes three parallel GET calls: (1) GET /api/v1/repos/:repoId — full repository metadata, (2) GET /api/v1/repos/:repoId/files — all file records (id, file_path, module_type, complexity_score, hotspot_score, is_hotspot, is_entry_point, language) without raw content — this drives the architecture map, (3) GET /api/v1/repos/:repoId/graph — dependency edges (source_file_id, target_file_id) for building the D3 graph. These three calls run in parallel using Promise.all. The workspace shell renders as soon as all three resolve.
TAB 1 — Repository Overview
Page Load
Calls GET /api/v1/repos/:repoId/overview. Returns: file_count, function_count, hotspot_count, language_breakdown (as a JSON object), documentation_coverage (percentage of files with non-null ai_summary), onboarding_progress (steps completed by this user / total steps), ai_summary, analyzed_at. This is a single aggregated query built in the Spring Boot service layer — not multiple separate calls.
TAB 2 — Architecture Map
Node Click — Opening the File Drawer
User clicks a node on the D3 graph. The frontend already has the file's id from the initial /files call. It sends GET /api/v1/repos/:repoId/files/:fileId. Spring Boot returns the full file record including ai_summary and the three most recent commits touching that file (fetched from the GitHub API at analysis time and stored in repo_files.last_commit_message). The frontend renders the right-side drawer with this data. No new analysis is triggered — all data is pre-computed and stored.
Heatmap Mode Toggle
No backend call required. The frontend already has hotspot_score and is_hotspot for every node from the initial /files response. Toggling heatmap mode simply re-colors all D3 nodes in-memory using the hotspot_score values. The risk color scale maps: 0–39 → emerald, 40–69 → amber, 70–100 → rose.
Ask AI about this file Button (in the File Drawer)
No backend call at click time. TAB 3 — Repo Chat (RAG-Powered)
Chat Session Creation
On first message send in a new session, the frontend sends POST /api/v1/repos/:repoId/chat/sessions with an empty body. Spring Boot creates a chat_sessions row and returns the sessionId. All subsequent messages in this conversation use that sessionId.
Sending a Message — The Full RAG Pipeline
User types a question and hits send. Frontend sends POST /api/v1/repos/:repoId/chat/sessions/:sessionId/messages with {content, contextFileId?, contextFunction?}. This is the most technically complex endpoint in the entire application:
▸  Step 1 — Load conversation history: Spring Boot fetches the last 8 messages from chat_messages for this sessionId, ordered by created_at. These form the conversation window for multi-turn context.
▸  Step 2 — Generate query embedding: Spring Boot calls the Gemini Embedding API with the user's question text. Receives a 768-dimensional query vector.
▸  Step 3 — FAISS similarity search: Spring Boot sends the query vector to POST /internal/search on the Python service, along with the faiss_index_id for this repository and k=8 (retrieve 8 most similar chunks). The Python service loads the FAISS index from disk (cached in memory after first load per worker), runs index.search(query_vector, 8), and returns the 8 nearest chunk IDs with their distance scores.
▸  Step 4 — Resolve chunks to files: Spring Boot maps the returned chunk IDs back to their source file IDs using the vector_chunk_ids arrays stored in repo_files. Deduplicates to get a unique list of cited files (typically 2–4 files). Fetches the raw_content of each cited file from PostgreSQL.
▸  Step 5 — Augmented prompt construction: Spring Boot builds a structured prompt for Gemini Flash. The prompt contains: (a) a system instruction describing the assistant's role as a codebase expert, (b) the retrieved file contents labeled by file path, (c) any contextFileId or contextFunction pre-loaded context, (d) the conversation history (last 8 messages), (e) the user's question.
▸  Step 6 — LLM call: Spring Boot calls Gemini Flash with the augmented prompt. Streams the response using Gemini's streaming API. As tokens arrive, they are forwarded to the frontend via SSE (Server-Sent Events) on the /chat/stream endpoint — the chat response appears word-by-word in the UI.
▸  Step 7 — Persist: Spring Boot inserts two rows into chat_messages: one for the user's message and one for the complete AI response (assembled from the stream), including cited_file_ids and tokens_used. Updates users.ai_tokens_used += tokens_used.
Suggested Question Pills Click
When a user clicks a suggested question pill, it pre-fills the input field with that question text. No backend call at click time. The user must still press send to trigger the RAG pipeline.

SECTION 06
Python Intelligence Service
AST parsing, dependency graphs, vector embeddings, and FAISS search
Responsibility Boundary
The Python FastAPI service owns exactly three responsibilities: (1) parsing source code into structured data, (2) building and querying dependency graphs, and (3) managing the FAISS vector index. It is not a public API — it is an internal service called only by the Java backend. It has no authentication, no database access, and no state beyond the FAISS index files on disk. It communicates exclusively with the Java backend via internal HTTP calls on a private network.
POST /internal/parse
Receives: {repoId, files: [{path, language, content}, ...]}. Processes every file:
▸  Python files: uses ast.parse(content) then walks the AST. For every ast.FunctionDef and ast.AsyncFunctionDef: extracts name, lineno, end_lineno, args.args (parameter names), returns annotation (return type). Computes cyclomatic complexity by counting: ast.If, ast.For, ast.While, ast.ExceptHandler, ast.With, ast.BoolOp (and/or count as +1 each), ast.IfExp. Base complexity = 1 + branch_count.
▸  TypeScript/JavaScript files: uses regex patterns to extract function declarations (function name(...)), arrow functions (const name = (...) =>), class methods. For complexity, counts occurrences of if, else if, for, while, catch, &&, ||, ternary operators using regex.
▸  Java files: uses regex for public/private/protected method signatures, counts if/else/for/while/catch/&&/||.
▸  Returns a JSON payload with functions, classes, imports, and complexity scores per file.
▸  Also builds a NetworkX DiGraph from all imports: calls nx.betweenness_centrality(G, normalized=True) to score each file's importance in the graph. Identifies entry_point nodes as nodes where G.in_degree(node) == 0. Returns the graph as an edge list with centrality scores.
POST /internal/embed
Receives: {repoId, files: [{fileId, content}, ...]}. Chunks each file's content into 512-token segments with 128-token overlap using a simple character-based approximation (1 token ≈ 4 characters). Batches chunk texts into groups of 100. For each batch, calls the Gemini Embedding API (models/text-embedding-004) and receives 768-dimensional vectors. Builds a faiss.IndexFlatL2(768) and adds all vectors. Saves the index to disk as {repoId}.faiss. Returns {faiss_index_id, chunk_count, chunk_to_file_map: [{chunkId, fileId, startChar, endChar}, ...]}.
POST /internal/search
Receives: {faiss_index_id, query_vector: [float x 768], k: 8}. Loads the FAISS index from disk (keeps a process-level LRU cache of the 5 most recently used indexes to avoid repeated disk I/O). Calls index.search(np.array([query_vector]), k) and returns [{chunkId, distance}, ...]. The Java backend uses these chunk IDs to resolve file content for the RAG prompt.
DELETE /internal/index/:repoId
Deletes the {repoId}.faiss file from disk. Removes the index from the in-memory LRU cache. Called by the Java backend when a user deletes a repository or triggers a re-analysis.
Technology Choices
▸  FastAPI: Async web framework for Python. Handles internal HTTP requests from the Java backend.
▸  ast (stdlib): Python's built-in AST parser. Used for Python file parsing. No external dependency required.
▸  NetworkX: Graph construction, centrality computation, and entry point detection.
▸  FAISS (facebook/faiss): Approximate nearest neighbor search for vector retrieval. Uses IndexFlatL2 (exact L2 search — fast enough at portfolio scale, no approximation error).
▸  google-generativeai: Gemini Embedding API client for generating 768-dimensional vectors.
▸  numpy: Required by FAISS for vector operations.

SECTION 08
Security, Scalability & Error Handling
Production-grade engineering decisions beyond the happy path
Security Decisions
▸  GitHub access tokens are AES-256 encrypted at rest in PostgreSQL using a server-side encryption key stored in environment variables. If the database is compromised, raw GitHub tokens are not exposed.
▸  JWT access tokens are RS256 signed (asymmetric). The public key is used only for verification — private key is server-only. If the JWT verification key were leaked, it could only verify tokens, not forge new ones.
▸  The internal Python service is protected by a shared secret header (X-Internal-Secret). Any request without this header returns 403. The secret is set as an environment variable on both services and never committed to the repository.
▸  All SQL queries use parameterized statements via Spring Data JPA. No string concatenation in queries — no SQL injection surface.
▸  All API endpoints that accept a repoId verify ownership before proceeding. A valid JWT is not sufficient to access another user's repository.
▸  Rate limiting is applied on auth endpoints using Spring's bucket4j integration: POST /auth/login is limited to 5 attempts per IP per 15 minutes. POST /repos/analyze is limited to 3 concurrent analyses per user on the free plan.
▸  CORS is restricted to the deployed Vercel frontend URL. All other origins receive 403 on preflight.
Caching Strategy
▸  Repository file lists (GET /api/v1/repos/:repoId/files) are cached in Redis for 5 minutes after first load. Invalidated when a re-analysis is triggered.
▸  FAISS indexes are cached in-process memory on the Python service (LRU cache, max 5 indexes). Loaded from disk on first search per server restart, then served from memory.
▸  Gemini API responses for per-file summaries are not cached — they are stored permanently in PostgreSQL and served from the database on subsequent requests.
Error Handling
▸  Every API response follows the same error envelope: {success: false, error: {code, message, details?}}. Error codes are machine-readable strings (REPO_NOT_FOUND, ANALYSIS_FAILED, TOKEN_LIMIT_EXCEEDED) so the frontend can render the appropriate UI state.
▸  Analysis pipeline failures: if any stage fails (GitHub API rate limit, Python service timeout, Gemini API error), the repository status is set to FAILED and the error_message field is populated. The frontend renders a red error card with the specific failure reason and a Retry button.
▸  Gemini API rate limits: if the embedding or summarization calls hit a rate limit, Spring Boot implements an exponential backoff retry strategy (3 retries, 1s/2s/4s delays). If all retries fail, the stage is marked as failed.
▸  GitHub API rate limits: the GitHub REST API allows 5,000 requests/hour for authenticated users. Large repositories with many files can approach this limit. If the rate limit is hit, Spring Boot pauses file fetching for the remaining rate-limit window and resumes, rather than failing the entire analysis.
Scalability Architecture
▸  Spring Boot backend is stateless (all state in PostgreSQL and Redis). Multiple instances can run behind a load balancer with zero coordination needed. Session affinity is not required because JWT authentication is stateless.
▸  The Python service is also stateless except for the FAISS index LRU cache. Multiple instances can run in parallel — each loads the FAISS index independently. Because FAISS index files are on Render's shared persistent disk, all instances share the same files.
▸  Analysis jobs are isolated per repository — one slow analysis does not block another. The Spring @Async thread pool is configured with a maximum of 10 concurrent analysis threads on the free-tier Render instance.
▸  PostgreSQL connection pooling via HikariCP. Pool size set to 10 connections (Supabase free tier allows 20 simultaneous connections).
Interview Story — What to Say When Asked About Technical Decisions
✓  KEY POINT
When an interviewer asks Why did you use FAISS instead of a managed vector database like Pinecone? — say: Pinecone's free tier expired after 30 days, which would have broken the demo. FAISS runs entirely on the Python service's disk with zero external dependency and zero cost. For a portfolio project at this scale (under 10 concurrent users), IndexFlatL2 with 768-dimensional vectors returns results in under 5 milliseconds — there is no performance justification for adding a managed service. In production, I would migrate to pgvector (PostgreSQL extension) which gives us vector search in the same database we already have.
✓  KEY POINT
When asked Why stream the AI response instead of returning it all at once? — say: A Gemini Flash response for a complex codebase question can take 4–6 seconds to generate fully. Returning it all at once means the user stares at a spinner for 6 seconds. Streaming via SSE means the first tokens appear in ~400ms and the user reads while the rest generates — it's a qualitatively different and much better experience, and it's the same technique used by ChatGPT, Claude, and GitHub Copilot Chat.
✓  KEY POINT
When asked What happens if the user submits a private repository? — say: The GitHub OAuth flow requests the repo scope, which grants read access to private repos. The user's GitHub access token is stored AES-256 encrypted in PostgreSQL. When the analysis pipeline runs, Spring Boot decrypts the token on the fly and uses it only for that HTTP request to GitHub. The token is never logged, never returned to the frontend, and is encrypted at rest so a database dump does not expose it.
